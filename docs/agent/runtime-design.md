# Hestia 后台 Agent 运行与首版验收设计

状态：draft-0.2，2026-10-25。依据 [ADR-0002](../decisions/0002-agent-led-consumer-workflow.md) 已确认的 Q1–Q8，配套 [工具边界](tool-contract.md)、[System prompt](system-prompt.md) 与 [模型策略](model-policy.md)。本文是可审查设计，没有接入模型、部署后台或执行验收。

定稿同步：用户于同日确认 [实现架构与技术栈](../web-stack.md) 及 [ADR-0003](../decisions/0003-modular-monolith-with-durable-workers.md)。统一 Worker 模型调用、SSE、pg-boss 与专用有限状态运行器作为执行基线；本文具体字段、参数和验收阈值仍需细化与实测，不能将架构确认视为全部契约或验证结果已完成。

## 1. 首版用户任务与输出

首版闭环：用户提供单层图纸和居住需求 → Agent 整理需求并理解图纸 → 校正空间初稿 → 设计布局与风格 → 用户采用 → 对话迭代 → 3D 与静态图。沿用既有单层、直墙及图片/PDF 选页的规划边界；CAD 原生识别、多层、结构改造和 room tour 不因本设计自动进入首版。

默认形成一个完整推荐；有实质取舍时最多提供两套，避免无意义地消耗时间生成相似结果。阶段是运行组织方式，不是每阶段都要求用户点击确认。已确认事实仍有效时直接沿用；首次空间确认与首次方案采用可以合并展示，但缺少可靠尺度或关键事实时不能跳过。

| 阶段 | 输出 | 用户何时需要参与 |
| --- | --- | --- |
| 需求与资料 | 有来源的需求记录、缺失资料和目标范围 | 仅补充影响设计的关键缺项或矛盾 |
| 空间初稿 | 原图叠加、墙/开口/房间候选、尺度状态和假设 | 校准必要尺寸、纠正或确认关键事实 |
| 布局与风格 | 同一建筑事实下的布局、家具组合、材质 | 可反馈偏好，不逐项批准生成过程 |
| 检查与比较 | 真实差异、需求满足情况、冲突和取舍 | 选择采用成果或提出进一步修改 |
| 应用与展示 | 当前方案修订、可撤销记录、3D/静态图 | 已明确局部修改自动应用；大方案采用一次 |

静态效果图与交互 3D 共享项目、资产和渲染规则；本轮不引入会改变空间结构的独立 AI 美化成片。展示质量是否达到用户预期需用实际渲染样例验收，不能只验证数据正确。

## 2. 运行位置与组件职责

平台模型调用和任务推进由服务端后台工作进程执行，浏览器关闭不终止已接受任务。浏览器仍负责用户输入、图纸预览、2D/3D 交互和状态订阅；不持有平台长期模型凭据。

| 组件 | 职责 |
| --- | --- |
| 项目与任务 API | 验证身份和项目归属，持久化任务创建、用户输入、候选选择和取消意图 |
| 持久化任务存储 | 保存状态、检查点、授权、候选、事件和用量；是任务状态事实来源 |
| 调度与后台工作进程 | 领取任务、维持执行租约、调度阶段、保存结果并处理中断 |
| Agent 运行器 | 构造上下文，调用模型，解析完整工具请求，控制循环和预算 |
| 供应商适配层 | 处理消息、图像、流式、工具调用、超时和用量差异 |
| 领域执行器 | 复核权限、版本、固定事实、几何、幂等和事务提交 |
| 渲染与输出服务 | 从指定修订生成成果；浏览器实时预览可使用同一数据但不是后台执行依赖 |

队列采用 pg-boss，模型调用使用 AI SDK Core，Hestia 维护专用有限状态运行器；具体模型供应商和云服务另定。调度通知可重复，数据库里的任务记录与租约才决定执行权。创建任务与投递必须具备可恢复性，优先验证同事务入队，不通过时使用同事务持久化待调度记录；不能依赖一次易丢失的内存消息。

### 2.1 统一对话入口与后台流式执行

统一入口、模型调用统一放在 Worker、回复流式返回已由 [ADR-0005](../decisions/0005-unified-conversation-entry.md) 确认；实现基线采用 AI SDK Core + pg-boss + Hestia 专用有限状态运行器，通过 SSE 交付持久化事件。以下流程作为实施依据，调度和批量参数需实测，尚未实现。

所有需要模型理解的用户消息先保存为对话轮次，再由 Worker 内的统一运行器调用模型。普通问答可在一次调用后结束，不必建立完整设计任务；混合消息中的操作创建或关联设计任务，回答与操作分别保存结果。选择对象、切换视角和读取项目不调用模型；明确的采用、取消按钮仍通过 API 直接记录和处理，不排队等待模型识别。

执行顺序：

1. API 验证身份，以客户端消息标识去重；在同一事务中写入消息、待执行轮次和可靠调度记录，提交后才返回接受结果和轮次标识。若响应丢失，客户端可按同一标识查询/重试而不生成第二轮。
2. Worker 领取轮次，读取选中对象、项目修订和已有任务上下文，开始一次模型调用，不再先调用一个分类模型。生成文本与工具请求允许交错；完整工具请求经程序校验后才执行。
3. 回复文本按短片段合并持久化，再通过带序号的事件流推送；不等整段回答或设计任务结束，也不逐 token 写库。项目变更在事务成功后发送结果事件；自然语言不得提前显示已完成修改。
4. SSE 只订阅已保存的事件，不拥有模型调用生命周期。订阅建立前已产生的事件也可以补读；关页不传播取消信号给 Worker。重开按轮次、任务快照与事件游标恢复，必要时以最新快照替代过期事件。
5. Worker 故障后从检查点和操作记录恢复，复核执行代次、意图与项目版本。文字流不是业务检查点；模型调用中断不能保证续接同一生成流，必要时新建输出尝试版本并明确替代中断片段，避免将重试文本拼成一次完整回复。已提交操作通过幂等记录避免重复执行。

对于“解释为什么不适合靠窗，同时把沙发右移 20 厘米”，可独立回答的解释边生成边显示，移动进入领域执行器；浏览器在操作前关闭也不会丢弃已接受的轮次。若问题依赖操作后的状态（如“移动后通道还剩多少”），须等实际检查/执行结果后回答。不会为了首字速度先猜测操作结果。

响应速度建议通过调度与流式交付保证，而不是维护一条请求内模型调用和一条后台模型调用：新消息的首次处理优先获得执行容量，长设计按有界阶段推进并公平调度，渲染与交互模型调用隔离并发；保留长任务进展机会，不能让连续聊天使其永久饥饿。同一项目的写入仍串行或经过版本保护，新消息不能绕过旧任务执行代次校验。

该方案会增加持久化、领取及事件转发开销，不能承诺与请求内执行零延迟差异。后续分别测量消息接收、排队、模型首片段和前端首片段的耗时，在实际模型与负载下确定阈值；不在讨论阶段承诺毫秒数。接受消息的即时状态反馈与真实模型回答分别显示。

## 3. 持久化对象与版本关系

推荐数据契约如下，字段细节在实现时统一建模：

- 设计任务：目标、范围、编辑目标、状态、阶段、用户意图版本、基础项目修订、预算、模型/工具/prompt 配置版本及取消标记。
- 需求记录：需求内容、用户消息来源、用户明确/确认/助手建议状态。更新后的要求覆盖旧要求时保留来源，不让聊天摘要变成新事实。
- 候选：基础项目修订、建筑事实与尺度状态、候选修订、相关需求版本、具体操作与对象、检查报告和展示记录。
- 用户输入与选择：应用生成的事件 ID、目标任务、问题或已展示候选引用。模型不能创建用户事件。
- 检查点：阶段成果引用、待处理事件、已完成操作、待查询外部请求、剩余预算。保存结构化状态及简短工作摘要，不依赖模型私有推理或内存 token 流恢复。
- 工具操作：应用生成的操作标识、输入摘要、前置版本、执行状态、结果、变更与用量引用。
- 输出成果：来源候选/项目修订、资产及渲染版本、检查覆盖、生成状态和文件引用。

一次已提交设计变更、对应新修订和幂等结果必须在同一事务中记录。消息状态和模型完成声明不替代事务结果。候选发生变化时，检查报告及确认记录不自动沿用。

## 4. 任务状态与恢复

状态由应用推进，不由模型随意设置。工具状态见工具契约，不能和这里的整项任务状态混用。

| 状态 | 含义 | 主要后继 |
| --- | --- | --- |
| `queued` | 已持久化，等待执行 | `running` / `cancelled` |
| `running` | 有合法租约，正在推进可执行阶段 | 等待、重试、取消或终态 |
| `retry_wait` | 可恢复故障，等有界退避或重新调度 | `running` / `partial` / `failed` / `cancelling` |
| `waiting_input` | 当前无可继续工作，缺少必要信息 | 新有效用户输入后 `queued`；或 `cancelled` |
| `waiting_selection` | 候选已就绪，等待采用或反馈 | 有效选择/反馈后 `queued`；或 `cancelled` |
| `cancelling` | 已记录取消，正在停止调用并核对在途操作 | `cancelled`，在途不明时保持此状态并恢复核对 |
| `completed` | 本任务请求的成果全部完成，所需提交/输出成功 | 新要求建立关联的新任务 |
| `partial` | 达上限或能力缺失，保留了可用部分成果 | 用户明确继续时重新调度，重新检查剩余预算与范围 |
| `failed` | 无法继续且未完成目标 | 明确重试后重新调度，不能丢弃历史操作和消耗 |
| `cancelled` | 已停止推进，并已核清在途项目提交 | 用户明确重新发起时建立关联任务 |

全套设计请求在等待用户采用时为 `waiting_selection`，不能提前标为 `completed`；若用户任务只要求比较候选，则展示完可完成。存在待答问题但还有独立工作时继续 `running`，记录问题并避免重复催问；没有有价值的可执行工作后才进入等待。

浏览器断开只移除状态订阅，不改变执行状态。重新打开时读取任务快照与持久化事件游标，补齐遗漏进度；不重新提交任务。流式文字用于展示，不是任务检查点。

工作进程领取任务使用有期限租约和递增执行代次。写入候选、任务状态与提交项目前验证当前代次；过期工作进程的迟到结果不能再写入。租约过期后，新执行者读取检查点及操作记录，先解决结果不明的操作，再继续下一步。

## 5. 新消息、版本冲突和取消

用户在生成中补充“保留现有书桌”时，API 先保存新消息、推进用户意图版本。后台在工具写入、展示、正式提交边界检查该版本；旧意图下产生的候选写入或展示结果不能标为符合新要求。保留已有成果中仍有效的部分，重新计算受影响部分，不要求用户重复整段需求。

同一任务的写操作串行化；独立识图、查询或渲染可以并行，但结果合并仍检查意图及项目版本。不同任务或手动编辑发生冲突时，不能用“最后返回者获胜”覆盖状态。首版默认同一项目仅一个会修改当前方案的活动任务，后续请求作为补充或等待；最终提交仍使用项目修订检查，不把调度串行当成唯一保证。

取消通过应用入口直达任务控制，不需要等待 LLM 理解。执行器在提交事务里检查取消状态：若取消先于提交生效，则不得提交；若提交先完成，保留真实修订并提供撤销，不谎称已经回滚。尚未核清的在途提交保持 `cancelling`，重启后继续核对。

向模型服务发送取消只能尽力停止远端生成，不能承诺撤回已发生的推理用量。迟到响应不再触发工具；远端已受理但结果丢失时，标记用量待核对，避免立即发起相同高成本请求。

项目修改保证幂等效果，不宣称所有外部模型请求严格只执行一次。外部调用是否支持请求查询与去重由适配器能力决定；不支持时，在剩余预算允许且不重复项目副作用的前提下有界重试，并保留不确定消耗。

## 6. 缺尺寸与概念草稿

尺度使用独立状态，不能靠助手一句“已确认”转换：

| 状态 | 可以推进 | 不能宣称或执行 |
| --- | --- | --- |
| `missing` | 需求整理、风格意向、拓扑与概念草稿 | 真实长度、面积、净距，或已确认空间采用 |
| `estimated` | 明示估算的示意布局与预览 | 把估算当实测，确认实际能放置 |
| `calibrated` | 按已知尺寸校准，继续交叉核对和几何检查 | 单凭已校准就认定所有房间、洞口和尺寸正确 |
| `conflicted` | 定位冲突，继续无依赖的需求/风格工作 | 忽略冲突采用受影响的空间数据 |

可靠尺度来源可以是用户提供的已知长度或可核对的图纸尺寸，不必须由用户逐面测量。校准来源和冲突检查留在数据里；一条可靠长度只确定尺度，不证明整张图没有畸变或识别错误。

“保存概念草稿”不同于“采用已确认空间”。首次采用前须有可靠尺度、关键轮廓/门窗及固定事实的可审查结果，并通过适用门槛；层高、材质等非关键默认项保留假设标记，不把每个默认值都变成单独确认步骤。

补充尺寸后，重新计算受影响的几何、摆放和检查结果，不仅更新文字。基于旧尺度的候选、确认和输出成果标记过期。概念输出在成果本身显示“概念草稿 / 尺寸未校准”，不只在聊天里提示。

## 7. LLM 调用契约与模型评估

首版仅平台模型，用户不需要挑模型或填写 API Key，具体组合未定。运行器通过供应商适配层提交任务上下文、消息、工具定义和应用生成的调用 ID，并接收文本片段、完整工具请求、结束原因、请求引用、用量及错误。

只有模型响应完整且工具参数通过校验后才执行工具。截断 JSON、重复工具调用事件、流式中途文本、模型自述的工具结果均不能直接写入项目。一个工具调用必须关联其真实结果后再继续；响应中途断线时保留可确认的结果，不能猜测剩余内容。

| 任务类型 | 需要验证的模型能力 | 程序负责的部分 |
| --- | --- | --- |
| 图纸理解 | 图像、文字和符号提取；不确定信息表达 | 图像预处理、尺度、图形关系和尺寸冲突检查 |
| 需求与设计规划 | 需求保持、取舍、跨步骤任务组织 | 固定事实、目录范围、布局搜索和可行性检查 |
| 精确局部编辑 | 对象/方向/单位理解，可靠工具参数 | 坐标换算、版本、权限、提交和撤销 |
| 成果解释 | 依据真实差异说明优缺点 | 面积、尺寸、检查覆盖和来源修订 |

复杂设计使用质量优先配置，明确局部修改使用速度优先配置；配置不等于必须使用不同模型。建议先验证一个主模型的两种配置，图像能力不足或局部延迟不达标时再评估专用模型；具体选择与升级、回退规则见 [模型策略](model-policy.md)。更换模型不能改变权限、工具、校验、确认或预算规则，也不能把不支持工具调用的文本回复转换为隐式命令。

任务保存模型、prompt、工具、规则和资产版本。供应商故障时只允许在已评估能力相当的配置间有限切换，记录切换；旧请求的迟到结果必须被执行代次拒绝。候选模型列表、数据发送目的地及重试策略属于平台配置，不由模型输出指定 URL。

质量与等待时间取舍已确认：复杂设计优先质量，局部修改优先低延迟；不给未经实测的时限或成本承诺。质量优先仍受总预算和停止条件约束，速度优先不省略必要校验。跨供应商使用资料的产品告知和配置应随实际供应商选定，不能假装已完成集成。

## 8. 成本边界与任务预算

这里的任务预算仅指平台模型与计算用量上限，不是装修预算或报价模块。建议限制单次调用、阶段、整项任务以及账号并发；具体数字依据样本测量设定。

开始调用前预留该调用允许的用量，重试、恢复和模型切换均计入原任务；完成后按实际用量结算。外部用量未知时暂不释放对应预留，避免未知请求加重复调用突破上限。不能承诺所有供应商的账单都能实时准确获知。

达到上限保存检查点并进入 `partial` 或 `failed`，明确成果与原因；不静默升级费用、不自动购买额度，也不让模型通过改任务 ID 重置消耗。产品是否提供付费重试、套餐或订阅另行设计，不在本 ADR 决定。

## 9. 首版验收矩阵

沿用授权、去标识的单层样本集计划：5 个清晰平面图、3 个扫描图、2 个手绘图，覆盖凹形、斜墙、缺尺度、尺寸矛盾和模糊门窗。样本是否齐备、模型识别率和修正耗时尚未测量，不将计划写成已有成绩。

| 维度 | 验收证据 |
| --- | --- |
| 完整用户任务 | 图纸与需求进入同一项目，初稿可纠错，候选可比较和采用，继续对话调整，生成 3D 与静态图 |
| 需求与设计质量 | 逐条比对关键需求，记录遗漏、取舍合理性及人工纠正次数；人工看实际空间和图像 |
| 执行边界 | 固定事实、越权、重复调用、过期确认、项目冲突、跨项目访问用反例验证；已知关键失败未修复不能发布 |
| 用户确认负担 | 无逐工具许可；必要信息与成果采用可识别，不重复追问已回答或已选择的内容 |
| 尺度 | 缺尺度仍有有用进展；概念稿明显标识；补尺寸触发重算及过期处理 |
| 关闭与恢复 | 关页后任务继续；重开可恢复进度和成果，未重复执行，等待选择不自动采用 |
| 崩溃与并发 | 领取后崩溃、提交后响应丢失、租约过期、旧结果迟到、新消息中途到达均可复现并正确恢复 |
| 取消 | 未提交的不再提交，已提交的如实保留；重启后能核清在途操作 |
| 输出 | 静态图与所标记的项目修订一致，文件可打开，候选和当前方案不混淆；首版没有伪装的视频按钮 |
| 模型与成本 | 相同样本记录完成率、错误类型、延迟、重试及用量；模型或 prompt 升级后复跑 |

最小演练任务：“根据图纸，为两人居住、有宠物且需要居家办公设计一套方案，保留已确认设施；比较一个替代摆法，采用推荐后微调书桌并导出静态图。”演练中加入一次关页恢复、一次缺尺寸补充和一次版本冲突。

测试替身可验证协议、重试和版本逻辑，不能证明真实模型识图可用。发布结论需真实模型调用、真实浏览器检查和视觉验收；当前本文仅定义验收，没有运行测试。

## 10. 后续实施依赖（未授权执行）

具体工作包、可复用能力和阶段退出标准以 [V1 实施计划](../v1-development-plan.md) 为准：

1. M0 验证真实模型、识图与渲染能力，确定数据契约和评估门槛。
2. M1 实现统一空间数据、命令执行器、必要几何检查、候选隔离、任务持久化与身份边界。
3. M2 尽早接入真实模型，以有可靠尺度的测试空间打通局部修改及基础后台恢复；协议替身同时覆盖失败路径。
4. M3–M4 扩展到图纸初稿、尺度与校正、需求保持和整套自主设计；局部修改演示不能代替这部分。
5. M5 完善后台输出及组合故障，M6 执行完整样本、真实浏览器与试用验收。

这些是依赖关系，不要求先做完完整设计器，也不构成实施授权。具体开发目录、依赖版本、调度产品和部署方式待技术验证后决定。
