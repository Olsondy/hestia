# 面向个人用户，由 Agent 主导设计流程，通过受限工具修改空间项目

Hestia 正从可操作的展示原型转向面向个人用户的住宅设计 Agent。用户已明确将 Agent、LLM 接入和输出约束作为当前设计重点，完整手动设计器不是主要交付功能。本 ADR 提议让 Agent 组织任务并提出结构化修改，由应用校验和提交；system prompt 指导行为，不能承担唯一的执行约束。

本文是待讨论草案，仅授权记录设计，不表示模型已经接入，也不替代现有已接受决策。

## 已确认方向与当前事实

- 用户明确当前优先设计面向个人用户的 Agent、LLM 接入及输出限制；完整手动设计器不是主要交付功能。
- 2026-10-25 第一轮 Q1 已确认：由平台提供模型。具体供应商、模型及计费未定；首版 BYOK 边界随后由 Q7 明确。此项确认不代表整份 ADR 已接受。
- 2026-10-25 后续 Q2、Q3 已确认：Agent 完成需求梳理、空间理解、方案设计、持续迭代与展示的完整设计任务；候选阶段自主连续推进，不逐步询问执行许可。采用初始空间或整套候选时确认，明确的局部修改可直接应用并撤销；固定事实变更单独处理。
- 2026-10-25 后续 Q4–Q6 已确认：首版完成单层图纸与居住需求到空间初稿、布局风格、选择采用、对话迭代和 3D/静态图的完整流程；room tour 后续扩展。缺尺寸时继续需求、风格及概念草稿，但确认空间尺度或判断家具能否放下前必须补充可靠尺寸。离开页面后任务在平台上限内继续，遇必要输入或成果采用时等待，重开可恢复，用户可取消。
- 2026-10-25 后续 Q7、Q8 已确认：首版仅平台模型，不提供用户 API Key/自定义端点入口；复杂设计在平台上限内优先方案质量，局部修改优先速度。两者使用相同的权限、固定事实和提交校验，不以速度换取绕过检查。
- 沿用 [ADR-0001](0001-fixed-facts-independent-of-layouts.md)：固定事实独立于家具布局。不能通过生成方案、换风格或模型修复错误绕过固定约束。
- 预算与报价继续排除。布局方案必须改变家具摆放或组合，换色属于视觉风格。
- 当前 `src/store.js` 的 `parseDemo()` 是规则匹配，`src/app.js` 的 `sendMessage()` 直接操作本地原型；尚无真实 LLM、通用几何校验或生产命令服务。
- 外部 `house-plan-designer` 已安装并预览自带示例。识图脚本和领域规则可评估复用；设计器 HTML 是否适合作为运行时组件仍待验证，不作为本 ADR 的前置依赖。

## 拟议决策

### 1. Agent 组织任务，应用拥有项目状态和执行权限

先采用单个主 Agent 调用有限工具。建议用户通过需求描述、对象点选和结果反馈推进设计，并保留校正和撤销入口。用户意图和当前选中对象进入上下文，模型读取所需项目事实，提出操作；应用负责识别目标、校验权限和几何、生成差异并按执行策略提交。手动微调与 Agent 使用同一条命令路径。

项目数据是空间事实来源，对话记录只保留交流过程。初次识图可以产生完整候选户型，但候选在确认前不覆盖正式项目；后续默认以稳定对象 ID 提交局部修改。模型不直接修改 Three.js 对象、数据库或任意 JSON 路径，也不生成可执行代码。

图纸识别、布局候选、局部编辑和展示输出分别是受限能力，不靠一个无限循环的提示词承担全部工作。尚未实现或尚未通过能力验证的工具不提供给模型。

移动、旋转、替换和撤销是底层操作示例，不是产品能力上限。已确认产品能力包括需求梳理、图纸理解与空间初稿、功能区与家具布局、风格材质、方案比较与迭代和效果展示；首版为单层空间的 3D/静态图，room tour 后续扩展。宏观任务可以组合多个受限操作，不要求用户逐条描述操作步骤，也不因此获得修改固定事实的权限。

例如“保留电视墙，把客厅改成能会客又能办公的两套方案”应转换为需求和约束，生成两组候选，分别校验并展示取舍。用户选定后再应用对应候选，不把一次高层请求简化为只能移动一件家具。

### 2. 输出分为用户说明和结构化工具请求

自然语言用于解释、询问和总结，不从自由文本中提取命令执行。涉及项目变更时必须调用工具，工具只接受列举过的操作类型、有效对象 ID、有限数值及允许的资产或材质 ID；拒绝未知字段和任意脚本。

工具按“查询、候选写入、正式提交、展示”分离；完整拟议契约见 [Agent 工具边界](../agent/tool-contract.md)。接口名称和字段仍属设计，不表示已有实现：

| 类别 | 职责 | 边界 |
| --- | --- | --- |
| 查询 | 读取项目摘要、对象、约束和已有方案 | 上下文只含当前任务所需数据；不可访问其他项目 |
| 提案 | 提交移动、旋转、替换、布局或识图候选 | 生成候选及差异，不直接写入正式项目 |
| 检查 | 校验候选的对象、版本、锁定和几何 | 由程序判断；模型不能自行宣布校验通过 |
| 执行 | 应用已授权且校验通过的候选，或撤销操作 | 由应用控制；模型不能伪造确认、解除锁定或绕过检查 |
| 展示 | 聚焦对象、切换视角和展示候选 | 与持久化设计变更区分；视频导出另行设计 |

#### 候选与当前方案分离

完整任务的推荐路径为：读取事实与需求 → 建立任务范围 → 创建候选 → 连续布局、配材质和检查 → 展示差异与取舍 → 用户采用 → 原子提交。候选有独立修订，不因预览、导出或模型说“完成”而成为当前方案。初次识图可以和布局一起形成候选；可靠尺度或关键固定事实尚未确认时，保留草稿并询问所需信息，不伪装为已确认空间。

高层请求授权 Agent 在指定范围内组合操作。例如设计整个客厅时，允许在候选中更换可移动家具组合；仅要求移动沙发时，不能顺带重排餐厅。允许的房间、操作类别、保留对象、用户明确要求和停止条件由应用维护，不由模型在工具参数里自行扩大。

#### 确认放在成果边界

| 情形 | 处理 |
| --- | --- |
| 读取资料、梳理需求、生成/修改/检查候选、展示预览 | 在任务范围内连续执行，不逐个确认 |
| 用户明确指定、目标唯一的单件移动/旋转或明确材质更改 | 校验通过即可应用，显示变化并提供撤销 |
| 用户采用初始空间、整套布局、家具替换或删除 | 展示具体候选后确认一次，不逐个确认内部操作 |
| 固定事实或锁定状态变更 | 独立的用户事实确认入口，普通设计工具不能解锁 |
| 目标歧义、必要尺寸缺失、需求互相冲突 | 询问阻塞结果的问题；同时继续无依赖的候选工作 |

用户对已展示的唯一候选说“采用 B”，可以由应用绑定该候选的具体版本作为确认，无须再问一次是否确定。确认不能仅由模型生成 `approved: true`；候选内容、当前方案或任务范围发生相关变化后，重新校验并按变化程度更新预览或确认。

Schema 校验只证明参数格式符合契约，不能证明意图理解正确或布局可行。几何通过也可能选错对象，因此必须结合点选上下文、歧义澄清和差异展示。

### 3. 在执行层强制约束，而不是只要求模型自律

- 执行时复核项目归属、对象存在性、可编辑字段、固定约束和项目版本；不能仅依赖 prompt 中的锁定描述。
- 每项提案绑定基础修订；发生并发编辑后重新读取和校验，不覆盖用户的新修改。
- 应用生成并保存操作标识，重复请求不得重复移动；同一批相互依赖的修改整体校验、整体提交，失败不留下半套布局。
- 用户确认绑定具体候选内容和版本。候选内容改变后，旧确认不能继续使用；明确局部修改按上述已确认策略自动应用，其余提交复核对应成果的确认。
- 几何检查区分硬冲突与使用空间提示。工具未覆盖的检查必须明确为未检查，不能声称安全、准确或符合工程规范。
- 完整设计任务按阶段保存检查点，不再将“整套设计最多 8 轮”作为目标。每阶段模型轮次、同一失败的修复次数和整项任务的调用量、耗时及成本都有应用上限；可用每阶段 8 轮、同一失败修复 2 次作评估起点，但任务总预算待实测确定。模型不能通过自建阶段、重命名错误或新建任务重置预算；到限后保存成果并报告未完成项，不循环询问“是否继续”以替代预算设计。
- 提案、执行结果与自然语言总结分开记录。只有收到执行成功结果，助手才能说“已修改”；取消或断线后先查询执行状态，再决定是否重试。

### 4. 平台提供模型，通过供应商适配层接入

运行器依赖统一的消息、工具调用、工具结果、流式状态和错误契约。供应商适配层处理具体协议；图片能力、工具调用和严格结构化输出分别验证，不能把“兼容协议”视为完整能力保证。不支持工具调用的连接只能讨论，不能静默降级为从文本猜测并执行修改。

模型、运行器、领域工具与渲染器相互分离，避免将更换模型变成重写空间逻辑。首版的供应商、模型和 SDK 版本由实际接入验证决定，本草案不指定未经验证的组合。

用户已选择平台提供模型并在关闭页面后继续执行，因此持久化运行器和平台模型调用必须独立于浏览器生命周期。设计采用服务端持有平台凭据、后台工作进程执行任务，浏览器负责交互和预览；这不等于已选定具体队列或云服务。平台长期凭据不能暴露给浏览器或模型。首版没有 BYOK、用户自定义 Base URL 或让用户挑选供应商的流程。

此前针对浏览器自接模型的密钥与调用建议是历史备选方案，首版不采用；当前 [已确认技术栈](../web-stack.md) 采用平台模型与后台 Worker。未来若重新引入 BYOK，需另立决策明确其密钥路径；不将它作为本轮尚待确认事项。所有密钥均不得进入 system prompt、项目内容或模型可见工具结果。

不同模型会影响识图、目标识别、需求追问、候选方案质量和工具调用可靠性。统一工具与校验可约束允许的状态变更，但无法保证不同模型理解相同、建议同样优质或识别出的事实一定正确。统一渲染器及资产版本可以减少呈现差异，不能修复错误输入。

建议先用同一套户型和任务评价候选模型，再决定单模型还是按识图、设计规划、简单编辑分配模型。记录事实识别错误、任务成功率、用户纠正次数、违规操作拦截、延迟和单任务成本；不得仅凭厂商通用榜单推断住宅设计效果。更换模型或 prompt 后复跑该样本集，权限和校验规则保持一致。

复杂设计与局部修改使用不同执行配置，具体路由及评估见 [模型策略](../agent/model-policy.md)。复杂设计允许在预算内多步推敲和比较，局部修改缩小上下文和可用工具以减少等待；不必因此部署两个模型或多个 Agent。应用决定执行配置，模型不能用切换配置扩大任务范围、预算或提交权限。

### 5. System prompt：任务组织与行为约束

详细正文独立维护在 [System prompt 草案](../agent/system-prompt.md)，不在 ADR 重复一份。它覆盖完整任务、自主推进、事实来源、候选与当前方案、工具使用、异常恢复和结果表达；工具参数约束以 [工具契约](../agent/tool-contract.md) 为准。

动态项目数据与最新工具结果按请求提供，不把上传资料或用户文本拼成系统指令。Prompt、工具契约、模型与资产版本共同记录并评估。低随机性和合法 JSON 均不能替代几何检查、意图判断或提交控制；不能仅凭模型遵循 prompt 就宣称系统满足边界。

## 考虑过的替代方案

- **在浏览器内运行完整 Agent**：易与原型连接，但关闭页面无法可靠继续，且不能让浏览器持有平台长期凭据。依据 Q1、Q6，设计转向服务端持久化任务；浏览器继续承担交互和 3D 预览。

- **先完成全功能设计器再接 Agent**：工具覆盖充分，但推迟验证 C 端主要交互。提议先做可运行的 Agent 闭环，按实际任务补齐编辑能力。
- **让 LLM 生成整份场景或执行代码**：初期灵活，但难以保证局部修改、固定事实和版本一致性。提议使用有限领域工具。
- **只靠 system prompt 限制输出**：集成简单，但模型误解或不遵守时没有强制边界。提议将权限和数据约束落实到执行层。
- **直接将外部 HTML 作为唯一项目底座**：可快速改善展示，但增量更新、状态回传和版本兼容尚未验证。本 ADR 不预先承诺此路径。

## 影响与现有规划的关系

依据已确认的 Q1–Q8，[V1 实施计划](../v1-development-plan.md) 已调整为“关键验证与契约 → 领域底座 → 真实 Agent 局部闭环 → 图纸与校正 → 整套设计 → 成果与恢复 → 样本试用验收”。完整手动界面不是当前主线，但 Agent 所需的领域操作和校验不能省略；局部闭环是内部里程碑，不能替代整套设计的首版验收。

当前已确认 Q1–Q8；工具契约、prompt、[后台运行及验收设计](../agent/runtime-design.md)、[模型策略](../agent/model-policy.md) 和实施计划是据此细化的待验证设计。旧范围文档保留为历史基线，实现技术栈已按 [已接受 ADR-0003](0003-modular-monolith-with-durable-workers.md) 定稿，邀请制账号与统一对话执行见 ADR-0004/0005；组件兼容性与工期仍需 M0 验证，旧开发顺序和估算已由新计划替代。具体部署技术、真实模型接入和外部渲染器复用均不因此成为已实施的事实。

## 决策树与设计收敛

已定前提：面向个人用户，优先设计 Agent 与 LLM 边界，完整设计器界面不作为当前重点。

1. **模型由谁提供？已确认。** 平台提供，后台执行不依赖浏览器存活；具体模型由业务评估选择。
2. **Agent 的产品任务边界？已确认。** 覆盖需求梳理、图纸理解、空间初稿、布局、风格、比较迭代和展示；room tour 后续扩展。固定事实变更仍走独立确认，不默认开放结构改造或工程判断。
3. **哪些修改需要用户确认？已确认。** 明确局部修改可直接应用并撤销；完整设计任务先在候选中连续工作，在采用初始空间或整套方案时确认，不逐个确认内部工具调用。
4. **首个闭环验收什么？已确认。** “单层图纸 + 居住需求 → 可纠正空间初稿 → 布局及风格 → 用户采用 → 对话迭代 → 3D 与静态图”。优先一个推荐，有实际取舍时最多两套候选；从工具子集开始实现是内部步骤，不以示例家具操作代替验收。Room tour 不在首版交付中。
5. **缺少关键尺寸如何推进？已确认。** 继续需求、风格和标注清楚的概念草稿；采用带尺度的初始空间或声称家具放得下之前，必须取得可靠尺度。估算不能自动成为确认事实。
6. **离开页面后的任务如何处理？已确认。** 平台任务在上限内后台继续，保存检查点；需要补充信息或采用方案时等待，重开恢复，用户可取消。

7. **首版模型入口？已确认。** 仅提供平台模型，不开放 BYOK 或自定义模型端点；用户不承担供应商配置。
8. **默认质量与速度取舍？已确认。** 复杂设计优先质量，局部修改优先速度；都遵守同一执行约束及平台上限。

本轮产品决策已收敛，不继续向用户询问已确认项或要求用户猜测技术参数。具体模型、任务预算数值、部署组件、渲染器接入和性能承诺属于后续验证事项；验证若揭示必须改变产品边界的冲突，再提出有证据的取舍。

整份 ADR 暂保留 proposed：Q1–Q8 为已确认决定，配套技术细节仍是待验证草案。设计基线确认与实施授权分开；用户当前明确只完善文档，不允许因此开始应用实现、安装依赖、部署服务或调用付费模型。将来确认整份 ADR 也不自动解除此限制。
