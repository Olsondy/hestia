# M06 跨企业隔离测试矩阵与两企业联合验收

日期：2026-11-10。范围：工单 #64，依据 ADR-0017。PostgreSQL 17.7（同 M01）。**状态：通过（自动矩阵 2026-11-10，浏览器联合验收 2026-11-11）。**

## 隔离矩阵（`isolation.integration.test.ts`，已加入 `pnpm test:db`）

- **做法**：遍历 `apps/web/app/api` 下的全部路由，对每个能指向另一家企业数据的路由与方法，在 A 的域名上分别以 A 的成员、A 的客户、未登录访客调用两次：一次带 B 的真实标识（企业、工作空间、方案需求、方案、分享码、分享、成员、项目、出图），一次带不存在的标识。要求没有一次成功，且两次的状态码和错误码完全相同，A 无从得知 B 的数据是否存在。
- **路由覆盖**：不带他企业标识的路由（自己的会话与积分、公开目录、登录注册、项目与工作空间列表）列在白名单里；新增路由既不在矩阵里也不在白名单里时，路由参数无法匹配，测试会失败。
- **对照**：同一套调用方式下，B 的成员在 B 的域名上能读到 B 的线索、访客能用分享码预览，说明矩阵能发现真正的泄露。
- **结果**：2/2 通过；231 次调用中，404（企业入口 / 不存在 / 分享码不可用）145 次、401 48 次，没有一次因来源校验被拒（403 `ORIGIN_REJECTED` 为 0）。另有 38 次（400 输入格式 34、415 4）在权限检查之前就因请求体不合格被拒，这些调用没有走到权限判断，对应接口的权限由各自工单的测试覆盖（M01、M02、S02、D08 等）。

## 两企业演示数据

`pnpm demo:seed --two-enterprises [--no-render] [--reset]`：保留原演示企业（`demo-home`）并登记域名 `a.localhost`，另建「演示家装企业乙」（`demo-home-b`，域名 `b.localhost`，独立成员、石材与软装目录、一个分享码）。同一个演示手机号在两个域名各自登录，是两个互不相干的账号。已在局域网开发数据库上运行一次（`--no-render`，未预生成效果图）。不带 `--two-enterprises` 时行为与之前相同。

## 浏览器联合验收（2026-11-11）

用户授权后，在局域网开发数据库上运行 `pnpm dev`，用 Playwright 无头 Chromium 打开 `a.localhost:3000`（演示家装企业）与 `b.localhost:3000`（演示家装企业乙）。H5 客户端查 390 与 1440；企业工作台按设计最小宽度 1024（`docs/design/WEB_UI_DESIGN.md`），查 1440，390 下横向滚动属预期。

| 检查 | 结果 |
| --- | --- |
| 首页与客户端按域名显示各自企业名称 | 通过 |
| 分享码：本企业的码打开方案；另一家的码（首页输入，或直接访问 `/s/<码>`）提示「分享码不正确或已失效」，与输错的码相同（390、1440，两个方向） | 通过 |
| 同一演示手机号在两个域名登录：两个不同账号；A 看到 A 的 2 个方案需求，B 显示「还没有项目」 | 通过 |
| A 客户的会话 Cookie 改放到 B 的域名（模拟生产环境的上级域名 Cookie）：`/api/session` 为 `null`，「我的」显示未登录、企业为乙 | 通过 |
| 成员在本企业工作台登录，各自只看到本企业的线索与动态 | 通过 |
| A 的成员在 B 的工作台登录（及反向）：留在登录页并提示「不是本企业的成员」；A 成员的会话 Cookie 带到 B 的工作台仍回到登录页 | 通过（修复后） |

验收中发现并修复两处：

- **跨企业登录工作台没有任何提示**：成员是平台账号，邮箱和密码正确，登录本身成功，但会话在另一家企业的域名上按未登录处理，页面静默回到登录表单。现在登录后若仍未登录，就清掉这个会话，并提示「不是本企业的成员」（`workbench-app.tsx`）。该提示只针对本人输入的正确邮箱和密码，不透露另一家企业的任何信息。
- **演示种子的成员密码与数据库不一致**：`private-data/demo/member.json` 是对另一个数据库运行种子时留下的，账号已存在时种子直接沿用保存的密码，不核对，导致 A 的成员无法登录。现在保存的密码与库里的不一致时，就用保存的密码重设（`scripts/demo-seed.ts`）。
