# 客户端调整页：多处修改累积后统一出图

H01 的调整页按服务端现有接口实现：客户每点一个选项就调用一次 `POST …/schemes/{schemeId}/adjust`，服务端校验通过即生成新修订并后台出图（约 1–2 分钟）。客户连改石材和铺法两处，就要等两轮出图，中间那一版也没有意义。用户于 2026-11-03 审阅 H5 原型 v2 时明确以客户体验为主，选择统一出图。

## 决定

- **交互**：调整页的修改（软装风格、石材、规格、铺法、波打线）先在客户端累积，界面列出「本次修改」并可逐处撤回；客户点「重新出图 · 生成修订 N+1」后，一次生成一个新修订、只出一次图。
- **校验**：累积期间按排版规则即时提示；有硬冲突时不能出图，冲突说明固定显示在操作按钮上方。服务端在提交时仍做最终校验，不通过则方案不变。
- **撤回**：出图前的撤回只撤销本地累积的修改；出图后回到上一修订仍沿用现有 `undo`（复用上一修订的效果图）。
- **确认**：出图完成后才能确认新修订；已确认后再调整，需要重新确认（沿用 H01）。

## 影响

- 服务端需要一个批量提交修改的接口（一次请求携带多处修改与 `expectedRevision`、`operationId`，原子地生成一个修订）。现有逐次 `adjust` 可保留给工作台使用。该接口在 H02 实现，不在本次原型改动内。
- `apps/web/components/client/client-request.tsx` 的 `AdjustView` 需要改为本地累积 + 统一提交；累积中的修改按 H01 的约定存在 sessionStorage。
- 原型 `example/prototypes/client-h5-v2` 按本决定实现，对照见 `docs/client-h5-design.md`。

## 考虑过的替代方案

- **每改一处即出图（H01 现状）**：服务端不用改，但客户连改几处就要等几轮出图，还会产生没有意义的中间修订。
